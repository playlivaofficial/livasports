## Architecture implemented

- LivaSports-owned canonical entities with branded internal IDs.
- Provider entity mapping with stable forward/reverse lookup and conflict protection.
- Sports-data and odds provider contracts separated by responsibility.
- Provider-specific HTTP and normalization code isolated below those contracts.
- Repository contracts and cache-first services between future frontend code and providers.
- Exact canonical selection and odds comparison rules suitable for a future slip.
- Server-only credentials and safe provider diagnostics.

Full design details and diagrams are in `docs/M1_ARCHITECTURE.md`.

## Provider boundaries

Sportmonks implements `SportsDataProvider` for competitions, seasons, teams, fixtures, scores, events, standings, lineups, statistics, and head-to-head.

OddsPapi implements `OddsProvider` for bookmakers, markets, and pregame odds. The gateway accepts one bookmaker per request, batches tournament IDs, shares cached responses, and observes an in-memory monthly budget. Its normalizer accepts only `MATCH_WINNER`, `TOTAL_GOALS`, and `BTTS`; Double Chance and every other non-V1 market remain disabled.

Unknown provider fixtures remain explicitly unmapped and produce no quote. Application components contain no provider URL or credential access.

## Known limitations and technical debt

- PostgreSQL repository implementations and executable ingestion jobs are not part of M1.
- OddsPapi fixtures still require a deliberate M2 reconciliation process to connect them to Sportmonks-backed canonical fixtures.
- Cache and provider-budget state are process-local; Redis or another shared implementation is required before horizontally scaled production.
- The request counter is a guardrail, not the provider's billing authority.
- Match Center payload shapes need licensed-response contract fixtures before building their UI.
- No database migration runner or rollback migration is wired yet.
- Affiliate link placeholders exist in the schema, but redirect and click-processing behavior is intentionally absent.
- Betano BR affiliate approval is not assumed.

## Risks

- Betsson's validated 50% fixture/market coverage means missing prices are normal and must remain visible as missing, never substituted.
- Provider fixture reconciliation errors could attach odds to the wrong match; M2 needs deterministic matching, ambiguity rejection, and review diagnostics.
- Process-local cache/budget controls do not coordinate multiple app instances.
- Provider payload changes require boundary contract tests and mapping review, not UI workarounds.

## Recommended M2 scope

1. Add PostgreSQL repository implementations and a migration execution workflow.
2. Build idempotent Sportmonks catalog/fixture ingestion for Brazil and Mexico.
3. Implement conservative cross-provider competition, team, and fixture reconciliation with an unresolved/ambiguous review queue.
4. Persist normalized current/history odds through cache-first scheduled refresh jobs, never visitor-triggered provider calls.
5. Add provider response contract fixtures for scores, events, standings, lineups, statistics, and H2H.
6. Expose internal server-side read models for real league/fixture data while retaining the M1 route skeleton scope until M2 acceptance.

M1 stops here. No M2 implementation was started.
